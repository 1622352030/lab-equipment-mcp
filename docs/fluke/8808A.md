## Manual and scope

| Item | Value |

The 8808A has no USB port. There is no separate programmer manual; chapter 4 of

**Terminal settings cannot be read back over the bus.** They are front-panel
only, so `fluke8808a_connect` takes them as arguments. Defaults are the factory
values; pass the panel values when they differ.

### Protocol (verified on hardware)

Every successful command is acknowledged. A query sends its data first and the
acknowledgement second; a non-query sends the acknowledgement alone:

```
*IDN?    -> b'FLUKE, 8808A, <serial>, 1.1r D2.0\r\n'  then  b'=>\r\n'
FUNC1?   -> b'VDC\r\n'                               then  b'=>\r\n'
*CLS     -> b'=>\r\n'                                        (one reply)
BOGUS    -> b'?>\r\n'                                        (one reply)
RANGE 99 -> b'!>\r\n'                                        (one reply)
^C       -> b'=>\r\n'                                then  b'=>\r\n'   (two)
```

Three details differ from the manual and each one cost a debugging round:

| Item | Manual | Hardware | Consequence if taken from the manual |
| --- | --- | --- | --- |
| Error prompts | `?` and `!` (4-24 figure 4-4) | **`?>` and `!>`** | Prompts go unrecognised and are parsed as data |
| Reply count after an error | — | **one**; no acknowledgement follows | A second read times out |
| `^C` acknowledgement | one `=>` (4-22 table 4-15) | **two** | The extra `=>` pollutes the next transaction |

**The acknowledgement must always be read.** Leaving it buffered shifts every
later reply by one — that is what the first hardware run did, and it forced a
rewrite of the protocol layer and its fake backend against raw byte captures.

### Front-panel echo (verified with echo enabled)

With the panel **Echo** setting on, the instrument prepends the command it
received, as its own message:

```
FUNC1?  -> b'FUNC1?\r\n'  then  b'VDC\r\n'  then  b'=>\r\n'   (three)
VDC     -> b'VDC\r\n'     then  b'=>\r\n'                     (two)
```

So echo adds exactly one message in front, and its text is the command as sent.
`fluke8808a_connect(..., echo=True)` tells the driver to expect it: every
transaction reads and discards that message first.

Two consequences worth knowing:

- **`VisaBackend.connect` cannot identify the instrument while echo is on.** It
  issues `*IDN?` atomically (write plus one read), so that read returns the
  echoed command rather than the identification. The driver reads past it and
  takes the next message as the identity — without that, connecting raises
  "Unexpected identification response".
- **The manual recommends leaving echo off** (4-4), because the echoed characters
  mix with the returned data.

**Secondary-display commands need the panel in dual-display mode.** With a
single display, `FUNC2?` and `MEAS2?` answer `!>` (an execution error), which the
manual describes as "发生执行错误" in table 4-9 but does not connect to the
display being off.

## Manual versus firmware

| Item | Manual says | Instrument does | Handling |
| --- | --- | --- | --- |
| Error prompts | `?` (syntax) and `!` (execution), 4-24 figure 4-4 | **`?>` and `!>`** | Driver matches the hardware spelling |
| Reply after an error | Not stated | **Error prompt only**, no acknowledgement | Driver does not attempt a second read |
| `^C` acknowledgement | One `=>`, 4-22 table 4-15 | **Two** | Driver reads both |
| `*RST` reply | Not stated; listed as a command (4-15 table 4-8) | **Answered, but only after the reset finishes: 2.8 s measured** — far slower than every other command | The acknowledgement is read like any other; a port timeout below ~3 s would misreport it |
| `*RST` scope | Table 3-9 lists nine items that return to the power-on state | Those nine return; **the output format (`FORMAT`) is not among them and survives the reset** | Nothing to correct: the table is the authority, and it omits the format |
| `*TST?` | "Always returns 0" (4-15 table 4-8) | **`?>` syntax error — not implemented on this build** | Call kept so the behaviour is visible; it raises on hardware |
| `MAXSET <value>` | Enters MAX mode and stores the value (4-18) | **Stores the value only; does not enter the mode** | Driver sends `MAX` first, then `MAXSET` |
| `MINSET <value>` | Enters MIN mode | Same as above | Driver sends `MIN` first |
| `MNMXSET <min>,<max>` | Enters MIN MAX mode | Same as above | Driver sends `MNMX` first |
| Secondary-display commands | "If the secondary display is not used, an execution error occurs" (4-16 table 4-9) | `FUNC2?`/`MEAS2?` answer `!>` | Panel must be in dual-display mode first |
| `RANGE <6\|7>` under VDC | Table 4-11A lists 6 and 7 for ohms/current only | `!>` execution error | Expected: the table maps ranges per function |
| ESB / MSS summary bits | STB bit 5 is the standard event summary and bit 6 the master summary (4-13 table 4-7) | **Neither sets**: after an unmasked command error, `*ESR?` reads 32 (CME) while `*STB?` stays at 16 (MAV) | The register model is readable and writable, but no summary bit was observed; a bus SRQ therefore cannot be relied on |
| `RATE?` reply | S / M / F | `S` | Accepted as-is |
| `*IDN?` fields | 4 comma-separated fields | `FLUKE, 8808A, <serial>, 1.1r D2.0` (spaces after commas) | Parser strips per field |
| `SERIAL?` | Returns the serial number | Returns it | Driver redacts it |

`MAXSET` was found on hardware on 2026-09-20: after `MAXSET 1.0` alone, `MOD?`
returned `0`; after `MAX` it returned `2`. This is the same class of
manual-versus-firmware gap as the SDG1062X `C1:SYNC?` reply.

## Acceptance

Evidence levels follow `references/acceptance.md`. `read-back` means the
instrument was queried after the write and returned the expected state;
`receiver-measured` means a second instrument produced a known stimulus and this
meter measured it.

### Input terminals

Voltage, resistance, frequency, continuity and diode tests use the **`VΩ` (HI)**
and **`LO`** terminals. Current functions must use the `mA` or `10A` terminal
instead; measuring current from the `VΩ` terminal reads near zero. The closed-loop
check below was taken with the red lead in `VΩ` and the black lead in `LO`.

### DC transfer against an SDG1062X (2026-09-20)

Red lead in `VΩ`, black lead in `LO`. CH1 set to DC, output enabled per point,
then disabled again. SDG1062X output accuracy is quoted as ±(1 % + 2 mV), so the
meter agreeing to about 1 mV is within the source's own tolerance.

| CH1 set | 8808A reading | Error |
| --- | --- | --- |
| +1.000 V | +1.001100 V | +0.001100 V |
| +2.000 V | +2.001600 V | +0.001600 V |
| −1.000 V | −0.999140 V | +0.000860 V |

CH1 was restored to `SINE 4 V, offset 0 V` with output off afterwards.

Two behaviours worth knowing when driving `COMP`:

- **`COMP?` answers `--` until a measurement completes.** The manual documents
  the dash (4-21 table 4-13); in practice a fixed level needs a few hundred
  milliseconds after `COMP` before the verdict appears, so poll rather than
  reading once.
- **`AACDC` reads near zero with the leads in `VΩ`**, which is expected: the
  current terminals are not connected.

The combined functions also append their own unit in format 2 (`VACDC`,
`AACDC`), which table 4-16 does not list.

### Not verified on hardware

| Feature | Why not |
| --- | --- |
| `RWLS` / `LWLS` | Locks the front panel and requires a deliberate release step |
| Secondary display (`FUNC2?`, `MEAS2?`, `MEAS?`) | The panel is in single-display mode, so the instrument answers `!>`; needs the panel switched to dual display |
| External trigger types 2..5 | Requires a TTL signal on DB9 pin 9, which is not wired |
| `*TST?` self test | Firmware answers `?>`, so the command is not implemented on this build |
| Service request end to end | `*ESE`, `*SRE` and `*ESR?` are accepted and read back, but no SRQ has been observed on the bus |
| Cold-start / power-cycle behaviour | Manual 4-4 notes baud rate, parity and echo survive power cycles; not re-tested |

## Troubleshooting

| Symptom | Check |
| --- | --- |
| No serial port in `fluke8808a_diagnose_setup` | Adapter not seated; the report lists every COM port and flags FTDI ones |
| `VI_ERROR_RSRC_NFOUND` | The COM port is not exposed by VISA; install a VISA runtime or open the resource by its exact `ASRL<n>::INSTR` name |
| Replies shifted by one | An acknowledgement was left unread; every command returns one |
| Replies shifted after print mode | `PRINT <rate>` leaves unsolicited readings and one stray `=>` in the buffer. Turn print mode off and drain the port before issuing further commands |
| Timeouts after connecting | Terminal settings differ from the panel. There is no read-back; pass the panel values to `fluke8808a_connect` |
| Garbled or partial replies | Parity or data bits differ from the panel setting (7 data bits is a valid panel choice) |
| `?` acknowledgement | Command syntax rejected. Unparseable commands also discard the rest of the line (4-7) |
