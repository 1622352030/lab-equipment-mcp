## 二、接口与会话设置

### 2.1 连接器 / 传输 / 协议（三者分离记录）

| 层 | USB 口 | RS-232 口 |
| --- | --- | --- |
| 物理连接器 | USB Type-B（后面板） | DB-9 插座（后面板） |
| 传输 | **USBTMC**（USB488 接口） | RS-232 串行（本机为 DTE） |
| 命令协议 | SCPI（IEEE 488.2 上层） | 同左 |

**依据**：编程手册印刷 p9「1.9.3 电子负载的 USB-TMC 功能」：`所有的电子负载功能都可通过 USB 编程`、`接口是 488.2 USB488 接口`、`设备能读懂所有的强制 SCPI 命令`、`设备是 SR1/RL1/DT1 使能的`。

**实机佐证**：Windows 设备管理器列出 **`USB Test and Measurement Device (IVI)`**，硬件 ID `USB\VID_2EC7&PID_8800\...`；VISA 资源为 `USB0::0x2EC7::0x8800::<序列号>::INSTR`。**该 USB 口不是虚拟串口。**

### 2.2 USB / USBTMC 会话

由驱动自动处理，无需配置：

```python
SessionConfig(read_termination="\n", write_termination="\n", query_delay_s=0.05)
```

依据：消息单元以 `<NL>` 结束（印刷 p4）；**每个响应以 LF + EOI 结束**（印刷 p5）。

### 2.3 RS-232 会话（**本次未在实机验证**）

面板 `Shift` + `System` 设置，存于非易失存储器；**手册未给出手厂默认值**：

| 项 | 手册列出的取值 | 驱动占位值 |
| --- | --- | --- |
| 波特率 | 4800 / 9600 / 19200 / 38400 / 57600 / 115200 | **9600**（占位，须与面板一致） |
| 奇偶 | `EVEN`（7 数据位）/ `ODD`（7 数据位）/ `NONE`（8 数据位） | `none` |
| 起始位／停止位 | **固定 1／1，不可编程** | 1 / 1 |
| 流控 | `CTS/RTS`、`XON/XOFF`、`NONE` | `none` |

引脚（印刷 p9）：1 无连接、2 TXD、3 RXD、4 无连接、5 GND、6 无连接、7 CTS、8 RTS、9 无连接。

> **注意**：RS-232 的波特率、奇偶与流控**只能从面板设置且命令不可读回**，因此驱动里的值是占位符，使用前必须与面板核对。**本接口本次未接实测线。**

### 4.5 负载侧保护参数的计算（电源侧按用户给定不变）

**电源侧保护由用户指定，保持不变**：OVP **20 V**、限流 **0.5 A**。

**第一步：列出实验工作点，找出最大值**

| 阶段 | 设定 | 实测电流 | 功率 |
| --- | --- | --- | --- |
| S3 CC | 0.10 A | 0.0994 A | 0.50 W |
| S4 瞬态 | 0.05 ↔ 0.20 A | 0.1999 A | 1.00 W |
| S5 CR | 30 Ω | 0.1658 A | 0.83 W |
| S6 CW | 1 W | 0.2001 A | 1.00 W |
| S7 CV | 6 V（源 8 V／0.2 A） | 0.1999 A | 1.20 W |
| S8 List | 0.05/0.12/0.20 A | 0.1999 A | 1.00 W |

**第二步：算 OCP**

$$I_{max} = 0.20\ \text{A},\qquad I_{peak} = 1.30 \times I_{max} = 0.26\ \text{A}\ (\text{CC 阶跃过冲按 30\%})$$

约束一：保护值须明显高于过冲 —— $OCP \ge 1.35 \times I_{peak} = 0.35\ \text{A}$
约束二：**负载保护必须先于电源限流动**，否则保护形同虚设 —— $OCP < I_{lim} = 0.5\ \text{A}$

$$\Rightarrow \boxed{OCP = 0.35\ \text{A}}$$

**第三步：算 OPP**（最大工作功率 1.00 W，过冲 1.30 W，CV 阶段最坏 $8 \times 0.2 = 1.60\ \text{W}$）

$$OPP \ge 1.5 \times 1.60 = 2.40\ \text{W} \;\Rightarrow\; \boxed{OPP = 2.5\ \text{W}}$$

**第四步：算延时**（瞬态切换过冲持续 < 100 ms）

$$\boxed{t_{delay} = 1.0\ \text{s}} \quad\text{——躲得过过冲，真过流时按限流 0.5 A 计仅累积 } 5 \times 0.5 \times 1 = 2.5\ \text{J}$$

**第五步：层次核对**

$$OPP\ 2.5\ \text{W} \;<\; POWer{:}CONFig\ 5.0\ \text{W} \;\ll\; \text{额定}\ 750\ \text{W}$$
$$OCP\ 0.35\ \text{A} \;<\; I_{lim}\ 0.5\ \text{A} \;\ll\; \text{额定}\ 6\ \text{A}$$

**最终参数**：`CURRent:PROTection:LEVel 0.35`、`:DELay 1.0`、`:STATe ON`、`POWer:PROTection:LEVel 2.5`、`POWer:CONFig 5.0`。

**原先的参数错在哪**（`OCP 0.45 A / 延时 3 s / OPP 3 W / POWer:CONFig 20 W`，工作点 0.30 A）：

| 问题 | 定量 |
| --- | --- |
| OCP 余量太紧 | 工作电流 0.30 A、过冲 0.39 A，离 0.45 A 只剩 0.06 A ⇒ 必然误触发（实测确实跳过闸） |
| 延时太长 | 3 s 累积 $5 \times 0.5 \times 3 = 7.5\ \text{J}$，是 1 s 方案的 3 倍 |
| 层次混乱 | 软件 OPP 3 W 与硬件功率保护 20 W 差 6.7 倍，谁先动作无法预期 |
| 工作点本身太大 | 0.30 A／20 Ω 把可用保护窗口挤到只剩 0.05 A |

### 5.1 覆盖审计（两个命令方向 + 一个工具面方向，可失败）

覆盖率的输入是**编程指南自己的命令索引**（`IT8800 Programming Guide-CN.pdf` 第 7–10 页），去掉 `[...]` 可选段后共 **135 条**。命令审计分两个方向，都落在 `tests\test_it8813.py` 里，都做过"能不能失败"的自检；第三个方向是 2026-09-22 补的**工具面**审计，落在 `tests\test_it8813_tools.py`：

| 方向 | 断言 | 它防的是 |
| --- | --- | --- |
| 驱动 → 手册 | 驱动发出的每条命令都必须在索引里 | 臆造命令（`MEASure:POWer?` 就是这样被实机抓到的） |
| 手册 → 驱动 | 索引每条命令都必须有实现，或显式列为范围外 | 漏做（少写一条命令不会有任何报错） |
| **驱动只读方法 → 工具面** | 驱动每个公开只读方法都必须有工具能到达（沿驱动 `self.<方法>` 调用图取传递闭包） | **可写却读不回**（见 8.3 节）：命令级审计看不见「方法实现了、却没暴露成工具」 |

**结论：135 条中 133 条有实现，2 条为本次范围外**（`REMote:SENSe`、`SYSTem:SENSe`，见 7.4 节第二类与第九节末四行）。

**第三个方向是 2026-09-22 补的**：前两个方向都是**命令级**的，判据是"这条命令驱动里有没有发"。
因此"命令发了、但只发在某个设置函数里，而没有任何工具能把它读回来"这一类，**两个方向都判不到**
—— 实测就是这样漏掉了 `POWer:CONFig`（硬件功率钳位）与 `VOLTage:ON`（导通阈值）：两者都能通过
MCP 写入，却在**任何只读工具里都读不到**，一次演示全程被 5 W 钳位限制而没有任何回读提示。
工具面反向审计落在 `tests\test_it8813_tools.py`，只有 `*OPC?` 作为同步握手具名豁免
（答案恒为 1，且每次写入驱动已用 `_sync` 发过）。

审计工具本身修过三次，每次都是真实踩到的盲点，记在这里是因为任何一个都能让"覆盖 100%"变成假象：

| 盲点 | 后果 | 修法 |
| --- | --- | --- |
| 只匹配 `self._write("X")` 形式 | 经 `_float_setting("CURRent:PROTection:LEVel", ...)` 等**位置参数**传入的命令全部看不见（约占驱动三分之一） | 改为收集源码中所有 SCPI 形状的字符串字面量 |

### 5.2 负载 CV 模式不能与恒压源对接（实测）

台架的直流源 M8811 是**恒压源**。一旦把 IT8813 也切到 CV，就构成了**两个电压源对接**：

| 项 | 实测值 |
| --- | --- |
| 电源设定 | 5.0 V，限流 0.5 A |
| 负载 CV 设定 | 4.9 V |
| 两者之间 | 只有约 0.07 Ω 线阻（0.1 A 时压降 0.0066 V；0.2 A 时 0.0141 V） |
| 要建立 0.1 V 压差所需电流 | 约 1.4 A |
| 实际结果 | 电流顶到电源限流 0.5 A，超过负载 OCP 0.45 A → **OCP 动作并锁存输入**（`INPut:STATe?` 回 0，需 `PROTection:CLEar` 才能恢复） |

**电路计算**（参数不是拍脑袋定的）：电源恒压 Vs、负载 CV 要维持端子电压 Vset，则负载必须吸收

$$I = \frac{V_s - V_{set}}{R_{line}}$$

$R_{line}$ 用两点法实测：0.0995 A 时压降 0.0065 V、0.1997 A 时压降 0.0136 V ⇒ **$R_{line} \approx 0.067\ \Omega$**。

- **原参数 4.9 V**（电源 5 V）⇒ $I = (5.0005-4.9)/0.067 = 1.50\ \text{A}$，是 OCP（0.45 A）的 3.3 倍 ⇒ **必然触发保护**。这就是错误所在。
- 在 5 V 固定不动的前提下，安全窗口只有 $V_{set} \in [4.970,\ 5.000]\ \text{V}$——窗口极窄，说明**不该把电源焊死在 5 V**。

**正确做法：改电源参数，把它变成电流源（两台设备联动）**

| 步骤 | 设置 | 结果 |
| --- | --- | --- |
| 1 | 电源 **12 V / 限流 0.2 A** | 负载只让电压升到 6 V 就开始吸流，电源被拉进 CC ⇒ 等效 **0.2 A 恒流源** |
| 2 | 负载 CV **6 V** | 电压由负载的 I-V 特性决定，CV 回路真正起作用 |
| 3 | 实测 | 负载电压 **6.000 V**（设定 6.0），电流 **0.2003 A**，输入未触发保护 |
| 4 | 测完改回 **5 V / 0.5 A** | 恢复本台架常规配置 |

校验：$6\ \text{V} \times 0.2\ \text{A} = 1.2\ \text{W}$（OPP 20 W 余量充足），$0.2\ \text{A} < \text{OCP}\ 0.45\ \text{A}$。

**结论与正确用法**：

- 负载 CV 模式**必须与电流源（或高阻源）配合**。与恒压源对接时电压由源和限流决定，负载的 CV 回路不控制任何东西，电流还会顶到保护。台架电源可以通过**压低限流**变成电流源，这才是 CV 该用的接法。
- 这一路没出事，靠的是**电源限流（0.5 A）与负载 OCP（0.45 A）构成的两层保护**：负载侧先动作。**不要为了"看得见电流"把限流抬到保护之上**，否则失去这一层兜底。
- 其余三种模式与恒压源配合都是标准用法：CC 恒流、CR 恒阻、CW 恒功率，实测分别得到 0.0995 A、0.2488 A、0.2002 A（设定 0.1 A、20 Ω、1 W）。

### 8.1 蜂鸣器（Buzzer）不是"报错指示器"

**不能拿响不响来判断命令是否出错。** 用户手册里蜂鸣器至少有四类触发：

| 触发 | 手册依据 | 属于报错吗 |
| --- | --- | --- |
| 警告提示 | 印刷 p3：「内建 Buzzer 作为警告提示」 | 广义告警 |
| **保护动作** | 印刷 p25：「如过压电路被触发，负载会立即 OFF，**蜂鸣器鸣叫**，状态寄存器中的（OV）和（VF）位被设置」（OVP／OCP／OPP／OTP 任一激活都会报警） | 是异常 |
| 开机 | 印刷 p16：「Initialize Power-ON Buzzer」 | **否** |
| 自动测试 | 印刷 p30：后面板外部信号接口的「自动测试提示音信号输出」引脚 | **否** |

而且**蜂鸣器可以在面板上关掉**：`Shift`+数字键 5 进 System 菜单 → **Buzzer** → ON／OFF（印刷 p13）。**编程指南全文没有蜂鸣器字样**，即**没有 SCPI 命令控制它**，只能从面板改。

后果有两个：「没听到响」**不能**证明没出错（Buzzer 可能被关）；「听到响」也**不能**断定是命令被拒（可能是开机音或保护报警）。

**判据要用寄存器**：`*ESR?`（bit5 CME／bit4 EXE／bit3 DDE／bit2 QYE，读取即清零）＋ `SYSTem:ERRor?` 队列，两者一起看。实测正是靠 `*ESR?` 才抓到 `trace_free` 的 `-230,"Data Corrupt or Stale"`（上游 `TRACe:DATA?` 超时留下的脏数据状态，属异常类而非拼写错）。

另外，手册（印刷 p25）说保护激活后「可以按前面板的**任意按键**来复位」—— 所以 `SYSTem:KEY` 模拟的按键**也可能清掉保护锁存**，用它时要放在复位之后并核对设置快照。

### 8.2 本机自检报告 `5,"RST section checksum failed"`（已知设备侧故障，非命令错误）

**现象**：调用 `*TST?` 时返回 `1`，错误队列出现 `5,"RST checksum failed"`，`*ESR?` 为 `8`（bit3），并且**蜂鸣器鸣叫一声、面板 Error 指示灯点亮**。

**编程指南印刷 p86 的自检错误码表**给出了确切含义（节选）：

| 码 | 含义 |
| --- | --- |
| 0 | No error |
| **1** | **Module Initialization Lost** ← `*TST?` 的返回值 |
| 2 | Mainframe Initialization Lost |
| 3 | Module Calibration Lost |
| 4 | Non-volatile RAM STATE section checksum failed |
| **5** | **Non-volatile RAM RST section checksum failed** ← 错误队列的值 |
| 10 / 11–16 / 20 / 40 / 41 / 80 | RAM、CVDAC／CCDAC／CRDAC 自检、Input Down、Flash 写/擦失败、Digital I/O 自检 |

该表标题同时写明「自检错误 0 到 99（**设置标准事件状态寄存器 bit 3**）」—— bit3 即 DDE，数值正是 **8**，与本机实测的 `*ESR?=8` 完全吻合。

**结论：这台设备的非易失 RAM 中「模块初始化数据」与「RST（复位默认值）段」的数据丢失或校验和不匹配。** 这类存储内容不由 SCPI 命令写入，**不是命令导致的**；本机第一次调用 `*TST?`（早于 `SYSTem:CLEar`／`*SAV`／`*RST` 等任何可能触及存储的操作）就已是此结果。

| 影响面 | 情况 |
| --- | --- |
| 已实测功能 | **不受影响** —— 424 条命令全部正常，测量偏差 0.02–0.58%，保护动作与锁存、四种模式、List、Trace 均符合预期 |
| **`*RST`／`SYSTem:PRESet` 的目标默认值** | **不可全信** —— 复位的目标就是那个校验失败的 "RST 段"。实测复位后读到 OCP 60 A／OPP 760 W／硬件 750 W（看似合理），但不能保证每次正确 |
| 蜂鸣器 / Error 灯 | 属"警告提示"：会鸣叫一声并点亮面板 Error（见 8.1） |

**处理**：功能层面可继续使用；若要消除该自检错误，需要恢复非易失存储内容（属厂商服务／校准范畴，手册的校准命令需要密码与 CAL 开关，见错误码 401–408）。本仓库的演示脚本因此**默认跳过 `*TST?`**（`RUN_SELF_TEST = False`），避免主动产生这条设备侧错误指示。

#### 8.2.1 定位到具体是哪一项不匹配：`TRIGger:SOURce`

「RST 段」装的就是各参数的 `*RST` 默认值，而这些值可读 —— 于是逐项验证：**把参数改成非默认值，再发 `*RST`，看是否回到手册规定的默认值**。

| 手册规定 | 实测 |
| --- | --- |
| `TRIGger:SOURce` 的 **`*RST 值 = MANUal`**（印刷 p33） | 设为 `BUS`／`TIMer`／`HOLD`／`EXTernal` 后各发一次 `*RST`，**四次全部保持原值**，一次都没回到 `MANUal` |

**同一批被改乱的其他 6 项，全部被正确复位**（CURRent、VOLTage、OCP、VOLTage:ON、TRACe:POINts、SENSe:AVERage:COUNt）—— 说明 **`*RST` 整体是有效的，坏的只是 `TRIGger:SOURce` 这一项**。

| 存储段／功能 | 状态 | 证据 |
| --- | --- | --- |
| **RST 段** | **校验和失败（码 5）**，其中 **`TRIGger:SOURce` 的默认值丢失** | 上表 |
| RST 段其余项 | 正常 | 同批 6 项正确复位 |
| STATE 段 | 正常（**未报码 4**） | 队列里从未出现 4 |
| 模块初始化 | 丢失（**码 1**） | `*TST?` 返回 1 |
| 用户寄存器 `*SAV`／`*RCL` | **正常** | 实测：保存 0.1 → 改到 0.02 → `*RCL 9` → 恢复 0.1 |

**实用结论：不要指望 `*RST`／`SYSTem:PRESet` 复位 `TRIGger:SOURce`** —— 必须显式写一次（`it8813_set_trigger_source(...)`）。其余参数可以依赖复位，但**本机 RST 段已报校验失败，复位结果不宜假设与手册逐条一致**。

**为什么"校验和失败"只表现为一项不响应、而不是整段错乱**：校验和是对整段的完整性校验，只要段内数据与记录的校验值不一致就会报错；具体表现可以是段内某一项无法正确恢复（本机即如此），也可以是更多项。因此**不要用"其它项看起来正常"来推断该段可信**。

### 8.3 「能写进去、读不回来」：工具面漏掉 34 个只读方法的坑

**现象**：演示中为了限功率把 `POWer:CONFig` 设成 5 W、把 `VOLTage:ON` 设成 0.1 V，
脚本结束后想确认"现在到底是多少"，却发现**没有任何只读工具能回答** —— `it8813_get_settings`
汇总了 23 个键，唯独不含这两项（新增后为 27 个）。

**根因**：命令覆盖审计（5.1 节）只看"手册里的命令驱动有没有发"，而这两个命令确实发了 ——
发在 setter 里。于是"驱动实现了只读方法、但没有任何工具调用它"这一类，在两个方向的审计里都是盲区。
修复前实测：驱动 189 个公开方法中有 **49 个任何工具都到不了**，其中 **34 个是只读方法**
（含上述两项、四模式的瞬态 MODE、斜率四查询、SENSe 两查询、输入定时、触发定时、四种模式的量程
边界、`MEASure:{VOLTage,CURRent}:{MAX,MIN}?`、`FETCh:TIME?` 等）。旁证：`it8813_fetch_voltage_max`
的文档字符串**已经在引用一个当时并不存在的工具** `it8813_measure_voltage_max`。

**修法**：新增 23 个只读工具（`it8813_*` 由 84 → 107），并把 `voltage_on`／`power_config`／
`input_timer` 并入 `it8813_get_settings`。守卫落在 `tests\test_it8813_tools.py`：
`test_every_driver_readback_is_reachable_from_a_tool`（**读回不可达数必须为 0**）与
`test_every_setting_that_can_be_written_can_also_be_read`（14 组"可写 → 可读"配对），
两条都带"能不能失败"的自检（驱动路径写错、豁免名单失效时会失败）。

**仍然不暴露的 15 个公开方法**（有意，不是遗漏）：12 个 setter（`CURRent`／`VOLTage`／
`RESistance`／`POWer` 的 `HIGH`／`LOW` 量程边界、`*ESE`／`*SRE`／`*PSC`、`SYSTem:POSetup`）
与 3 个动作（`*TRG`／`*OPC`／`*WAI`）。量程边界与 `SYSTem:POSetup` 的**读取**已由新增 getter
覆盖，而它们的**写入**方向没有工具 —— 本轮只修"能写却读不回"这一侧，**不可写就不可怕**；
`*TRG` 与已暴露的 `it8813_trigger` 语义重复。

### 8.4 `*RST`／`SYSTem:PRESet` 在 LIST 模式下被整段忽略，且不报错

**现象**：`FUNCtion:MODE` 为 `LIST` 时执行 `it8813_reset(confirm=True)`／`it8813_preset(confirm=True)`，回执都是成功（`{reset: true}`／`{preset: true}`），但**逐项核对发现没有一项被复位**，**错误队列为空**（CC 设定 0.15 A、量程 6 A、OCP 0.35 A/ON/1 s、OPP 2.5 W、`POWer:CONFig` 5 W、`VOLTage:ON` 0 V、`INPut:TIMer:DELay` 6 s、`TRIGger:SOURce` TIMER 全部保持原值）。

**定位**：先 `it8813_set_function_mode("FIXed")` 退出 LIST，再发同一条 `*RST` → **复位了 13 项**（CC 0.15→0.0 A、量程 6→60 A、OCP 0.35 A/ON/1 s→**60 A/OFF/3 s**、`VOLTage` 6→120 V、`RESistance` 20→7500 Ω、`POWer` 0.5→0.0 W、OPP 2.5→**760 W**、`POWer:CONFig` 5→**750 W**、`VOLTage:ON` 0→0.1 V、`INPut:TIMer:DELay` 6→10 s）。故 **no-op 由 LIST 模式引起**，与 RST 段校验和失败无关。

**处理**：① 复位前必须先退出 LIST 模式，否则复位**静默失效**、没有任何提示；② **复位会把三层保护放回宽松默认**（OCP 60 A、OPP 760 W、硬件钳位 750 W），复位后必须显式重设（本演示的复位就是靠这一步回到安全态）；③ `TRIGger:SOURce` 即便复位生效也不回 `MANUal`（见 8.2.1），必须显式写一次。

### 8.5 `INPut:SHORt` 会吸一个 8–11 A 的瞬间尖峰，随后锁住设备

**手册措辞**（印刷 p40）与驱动的原描述都是"使模块吸取当前量程允许的最大电流"。

**第一次演示只看到稳态**，据此误判为"不吸流"：

| 步骤 | 读数 |
| --- | --- |
| 输入 ON（CC 0.0 A）、`it8813_set_input_short(True)` | 回执 `enabled: true`，`INPut:SHORt?` 读回 **1** |
| 立即两侧测量 | **负载 0.0 A ／ 5.00082 V（开路电压）；电源 0.0 A ／ 4.9994 V** |
| 断开输入后再 `set_input(ON, confirm=True)` | **被拒**：`requested: ON`、读回 `enabled: false`、`applied: false` |
| 先 `set_input_short(False)` 再使能输入 | **仍被拒**（说明拒绝不是"短路联锁"，而是设备处在锁定态） |
| `STATus:QUEStionable:CONDition?` | **24578 = bit1＋bit13＋bit14**（bit1 即"电流"位） |
| `it8813_clear_protection()` → 再使能输入 | **成功**（`applied: true`），随后 CC 0.1 A 正常吸流 0.0984039 A |

**第二次演示用窗口极值抓到了真相** —— 尖峰确实存在，只是稳态看不到（负载侧 `MEASure:CURRent:MAX?`）：

| 同一测量窗口内的操作 | `measure_current_max` | 同期电源侧读数 |
| --- | --- | --- |
| 触发后的窗口基线（已含动态运行与量程 6→60→6 往返切换） | 0.532669 A | — |
| 在该窗口内对**正在吸 0.0987 A** 的负载执行一次 `it8813_set_input_short(True)` | **8.34317 A** | **0.0 A** |
| （第一次演示的旧窗口，含同一次短路） | **10.7378 A** | 未记录 |

**结论**
- **短路瞬间负载侧出现 8.3–10.7 A 的电流尖峰**（两次独立测量，量级一致），而**同一时刻电源侧读 0.0 A** —— 尖峰极短，电源的限流环来不及响应，其串口慢查询也抓不到。这正是"电源侧控制环慢于负载侧检测、负载先看到大电流"的表现。
- 尖峰之后**负载自身保护关断输入级**：稳态 0 A、`questionable condition` 置 bit1（SCPI 的"电流"位）、且必须 `PROTection:CLEar` 才能再使能输入。
- **带电短路应当避免，与电源大小无关**：短路电流由**电源侧**决定，**电源越强、尖峰越大、能量越高**，所以"小电源才要小心"是反的。对电源而言这是滥用，不是测试手段。
- **它也达不到"验证保护"的目的**：尖峰远短于 OCP 延时、稳态又是 0 A，OCP 路径根本不会被激发，而设备会被锁住（须 `PROTection:CLEar`）。**因此 `INPut:SHORt` 在这里没有任何正当用途。**本演示执行它只是出于"逐项覆盖工具"的要求，不是推荐做法。
- **量程切换已被排除**：同一窗口里做过 6→60→6 往返切换，贡献 ≤ 0.53 A。
- **测量方法学**：负载侧的 `MEASure:{VOLTage,CURRent}:{MAX,MIN}?` 能抓到毫秒级尖峰，电源侧的串口慢查询不能；且 `it8813_trigger()` 会**重开测量窗口**，所以窗口基线必须在触发**之后**、动作**之前**取。

### 8.6 List 与 Trace 不能同时采集：`TRACe:DATA?` 沉默超时

**现象**：List 配好、`TRIGger:SOURce` 为 `BUS`、使能输入并 `it8813_trigger()` 之后读 `it8813_read_trace()` → **VISA 超时**（`VI_ERROR_TMO`），而**错误队列为空**。

**定位**：随后 `it8813_get_trace_settings` 显示 `feed_control` 已被设备自动改成 `NEVER`、`free` = `"100,0"` → **缓冲里 0 点数据**。即**一次 BUS 触发被 List 引擎消耗，Trace 未获采样**；`TRACe:DATA?` 在空缓冲上**不报错、只沉默**，表现为超时（与"手册外命令"的表现同类，见第八节首表）。

**处理**：① 不要在 List 运行时用 Trace 采同一段波形，List 的运行改用**连续测量**观察阶梯（实测采到 0.1498→0.1001→0.1500 A）；② Trace 超时后**先断输入再做诊断**，并**回读确认**断开（超时后不要只信回执）；③ 采集前确认 `free` 有空间、`feed_control` 不是 `NEVER`。

### 8.7 两个"守卫测试只测了拒绝路径"的盲点（代码侧，已修）

`it8813_write_scpi` 调用的是 `it8813.write(...)`，而驱动里写命令的方法是私有 `_write` → **任何调用都失败**（实机报 `'IT8813' object has no attribute 'write'`）。原有两个测试（缺 `confirm_unsafe`、传查询）**都在执行到该行之前就抛错**，所以成功路径从未被覆盖 —— 与 5.1 节那个"命令级审计看不见方法级缺口"是同一类盲点。

**修法**：驱动补公开入口 `write_raw()`／`query_raw()`（`it8813_query_scpi` 原先也在用私有 `_query`），server 改用公开入口；新增 3 个**成功路径**测试（其中一个直接断言命令被送到驱动）。实机复验分两层：① 驱动层 —— `write_raw("CURRent 0.12")` 之后 `query_raw("CURRent?")` 读回 `0.12`，恢复后读回 `0.1`，队列为空；② **服务重启后走 MCP 工具层** —— `it8813_write_scpi("CURRent 0.12", confirm_unsafe=True)` 返回 `{"command": "CURRent 0.12"}`（修复前此处必定抛 `'IT8813' object has no attribute 'write'`），随后 `it8813_query_scpi("CURRent?")` 读回 **`0.12`**，确认写入真的到达设备、不只是回执成功。
